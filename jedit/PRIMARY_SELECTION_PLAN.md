# Making the X11 primary selection fold word glyphs

Read `WORD_CLIPBOARD_PLANS.md` beside this file first: it carries the implementation
order, the decisions the user has settled, the conventions all four plans follow, and what
has already been reviewed.

A work plan, the **second** of four. `WORD_BOUNDARY_PLAN.md` goes in first and rewrites the
two functions this one calls; `DRAG_AND_DROP_PLAN.md` and `SEARCH_FIELD_PASTE_PLAN.md` are
the other two. Read `../fonts/WORD_GLYPHS.md` first; it defines the feature all four extend.

Source read from the Isabelle component's own jEdit tree:

    contrib/Isabelle2025-2/contrib/jedit-20251128/jedit5.7.0-patched/jEdit/

**Convention.** A claim marked *measured* was produced by running code — jEdit's repackaged
BeanShell out of `jedit.jar`, under `xvfb-run` for anything touching a real X11 selection.


## The problem

X11 has two clipboards. One is the ordinary clipboard that Ctrl-C and Ctrl-V use. The other
is the **primary selection**: whatever you last selected with the mouse goes into it
automatically, and a middle click pastes it. `phi_word_clipboard.bsh` fixes the first and
does not touch the second.

phi-System draws each keyword as one glyph on a Unicode private-use code point, so
`\<pending>` is the single character U+E048 in the buffer. Selecting it with the mouse and
middle-clicking into a terminal hands that terminal U+E048, which has no meaning outside
PhiSymbols. **In the default configuration, today.**


## What is broken, verified

jEdit maps the primary selection to its `%` register: `Registers.java:610-612` runs
`Clipboard selection = toolkit.getSystemSelection(); if(selection != null)
registers['%'] = new ClipboardRegister(selection);` in a static initialiser.

Two places write it, and only two (`grep` over the whole tree):

* `TextAreaMouseHandler.java:539-541`, after a mouse selection:
  `if(dragged && sel != null) { Registers.setRegister('%',textArea.getSelectedText(sel)); ... }`
* `Gutter.java:1148-1152`, the same for a gutter line selection.

`Registers.setRegister(char,String)` (`:464-467`) is `setRegister(name, new StringSelection(value))`,
and `setRegister(char,Transferable)` (`:474-490`) calls `register.setTransferable(transferable)`
on the existing register object. So the text goes out as a bare `StringSelection`, never
consulting the `datatransfer.TransferHandler` service list that the copy fix hooks.

**The write is not gated by the quick-copy preference**, which is what makes this reachable
at all: the call at `:541` sits **outside** the `if(quickCopyDrag)` guard at `:542`. The
preference gates only the two *paste* sites, `:546` and `:561`.

**And in Isabelle/jEdit the preference is on anyway.** `view.middleMousePaste=false` is
stock jEdit's default (`jedit.jar`'s `org/gjt/sp/jedit/jedit.props:292`), but Isabelle ships
a site-properties file that overrides it —
`contrib/jedit-20251128/jedit5.7.0-patched/properties/jEdit.props:359` contains
`view.middleMousePaste=true`, generated by `src/Pure/Admin/component_jedit.scala:445`.
`jedit_main.scala:119` sets `jedit.home` to that directory, `jEdit.initSiteProperties`
(`jEdit.java:3595`) loads every `*.props` under it as site properties, and its own comment
says site properties are "loaded as default properties, **overwriting** jEdit's system
properties". So middle-click paste is live by default, and the fold direction of this work
is a **default-on, user-facing behaviour change**, not an opt-in edge case.

**The read direction is unfixed too.** `Registers.paste` reads `reg.getTransferable()`
(`:244`) and the existing script wraps only register `$` (in `phi_word_install`),
so a middle-click paste of mathematical letters from another application does not fold.

**Isabelle does not touch `%`.** Its only register use is `'$'` — `Registers.copy` at
`pretty_text_area.scala:350`, `Registers.cut`/`paste` at `jedit_accessible.scala:239,245`.

**On platforms with no primary selection**, `getSystemSelection()` returns null and
`registers['%']` starts null — but not for long: `Registers.setRegister(char,String)` falls
through to `setRegister(char,Transferable)`, whose `else` branch at `:484-489` creates a
`DefaultRegister` and stores it. So on Windows and macOS the first mouse selection installs
a plain in-JVM register at `%`, unwrapped.


## The mechanism

`Registers.Register` (`Registers.java:678-701`) is an interface with four methods:
`toString`, `setValue`, `getTransferable`, `setTransferable`. The existing script already
wraps register `$` through it, in `phi_word_install`, so the technique is not new here —
this reuses it.

The one difference from `$` is which half needs work. For `$`, the outgoing direction is
handled by the service list, because `Registers.copy` builds its transferable through
`datatransfer.TransferHandler.getInstance()`; the wrapper only folds on the way in. For
`%` there is no service list on either side, so **the wrapper expands in `setTransferable`
and folds in `getTransferable`**.

```
phi_install_primary_selection()
{
    phi_inner = Registers.getRegister('%');
    if (phi_inner == null) return;              // no primary selection on this platform
    phi_sel = new java.util.HashMap();          // this wrapper's own slots; NOT top-level
    phi_w2 = new Registers.Register() {
        public String toString() { ... }
        public void setValue(String v) { this.setTransferable(new StringSelection(v)); }

        public void setTransferable(Transferable t) {
            try {
                if (t != null && t.isDataFlavorSupported(DataFlavor.stringFlavor)) {
                    phi_original = t.getTransferData(DataFlavor.stringFlavor);
                    if (phi_original != null) {
                        phi_expanded = phi_word_expand(phi_t, phi_original);
                        phi_sel.put("original", phi_original);
                        phi_sel.put("expanded", phi_expanded);
                        phi_inner.setTransferable(new StringSelection(phi_expanded));
                        return;
                    }
                }
                phi_inner.setTransferable(t);    // inside the guard, not after it
            }
            catch (Exception e) { }
        }

        public Transferable getTransferable() {
            phi_outer = null;                            // bound before the try can fail
            try {
                phi_outer = phi_inner.getTransferable();
                if (phi_outer == null) return phi_outer;
                if (!phi_outer.isDataFlavorSupported(DataFlavor.stringFlavor)) return phi_outer;
                phi_s = phi_outer.getTransferData(DataFlavor.stringFlavor);
                if (phi_s == null) return phi_outer;
                phi_e = phi_sel.get("expanded");
                if (phi_e != null && phi_e.equals(phi_s)) return new StringSelection(phi_sel.get("original"));
                return new StringSelection(phi_word_fold(phi_t, phi_s));
            }
            catch (Exception e) { return phi_outer; }
        }
    };
    Registers.setRegister('%', phi_w2);
}
```

The details below are not decoration.

**`phi_outer` is bound to `null` before the `try`, not inside it.** The `catch` returns
`phi_outer`, so if the very first statement — the `getTransferable` call — is what throws,
an unbound `phi_outer` would make the `catch` itself fail and the error would escape onto
the AWT event thread, which is the one place this wrapper must never break.

**`phi_t` comes from `WORD_BOUNDARY_PLAN.md`**, which hoists the generated table to a
top-level name. Without that this sketch has nothing to pass: **measured**, transcribed
literally against a real `Toolkit.getSystemSelection()`, the first write to the register
fails outright.

**`phi_sel` lives inside the install function, not at the top level.** With one shared
top-level map, a second install silently breaks the read-back — **measured**: after
`phi_install_primary_selection()` runs twice, writing `U+E048` still puts the right letters
on the selection, but jEdit reads back the mathematical letters instead of the glyph,
because the outer wrapper stores into the same map the inner one reads.

**The fall-through `phi_inner.setTransferable(t)` sits inside the `try`.** Written after it,
a clipboard write that throws would be swallowed by the `catch` and then retried unguarded,
so the second throw escapes onto the AWT event thread.

**The name is `phi_w2`, not `phi_w`.** `WORD_BOUNDARY_PLAN.md` records the measured
BeanShell rule that a method assigning a bare name writes through to an existing global of
that name, and startup scripts share one namespace. `phi_w` does not exist yet when this
plan lands — `DRAG_AND_DROP_PLAN.md`, which is implemented after it, will take that name —
so the point is to leave it free rather than to avoid a present collision.

**No `phi_word_fold` post-processing is needed.** `WORD_BOUNDARY_PLAN.md` puts the
joiner-stripping inside `phi_word_fold` itself precisely so that no consumer has to remember
it. An earlier draft of that plan used a separate helper and a list of call sites, and this
plan was one of the two that forgot to call it.

### Why the two remembered slots

Expansion and folding are not exact inverses for every input; `WORD_BOUNDARY_PLAN.md` sets
out the shapes and the measurements. Remembering the last string we put out, and the text it
came from, makes the jEdit-internal round trip exact.

**The match is not infallible, and the plan should not claim it is.** An earlier draft said a
foreign owner's string "simply fails to match". It can match: **measured**, after
`setRegister('%', \<pending> + bold "zzz")`, another application publishing exactly those
literal bold letters makes jEdit paste back `U+E048` plus the letters — the memo fired and
returned the remembered original where folding would have left the text alone. This is
narrow (the foreign string must be character-for-character what we last published) and its
result is the text the user last selected in jEdit, so it is not corruption; but it is a real
behaviour and manual check 2 below is designed around it.

**Always return a fresh `StringSelection` from `getTransferable`.** The reason is simply that
the value we hand back differs from what is on the selection. It is **not**, as an earlier
draft said, that re-using the clipboard's own transferable would cost a second X11 fetch:
**measured** with a separate JVM owning the selection and counting fetches on the owner side,
`sun.awt.datatransfer.ClipboardTransferable` fetches every flavor eagerly in its constructor
and serves later `getTransferData` calls from that cache — one owner-side fetch either way.
What does cost a second blocking fetch is a second `getContents`, which is why the `catch`
above returns the already-obtained `phi_outer` rather than calling `phi_inner.getTransferable()`
again.


## Two small decisions

1. **`toString()`.** It has no consumer in the shipped configuration:
   `RegisterViewer.refreshList()` skips `%` outright (`:200-201`, `if (i == '%') continue;`)
   before ever calling `reg.toString()`, `handleRegisterChanged` ignores its change events
   (`:128`), `JEditRegisterSaver.saveRegisters` short-circuits on `%` (`:112-115`), and
   `RegisterChanged.getRegisterValue()` has no caller in the tree. **Recommended: delegate to
   `phi_inner.toString()`** — the cheap branch — and say in a comment that nothing reads it.
   An earlier draft claimed the register viewer displays it; it does not.
2. **Exceptions.** Every method body wrapped in `try`/`catch(Exception)`, degrading to the
   unwrapped register. Note the limit `WORD_BOUNDARY_PLAN.md` and `DRAG_AND_DROP_PLAN.md`
   both record by measurement: BeanShell's *own* interpreter errors — an unbound name, an
   unresolved method — are `EvalError`s that neither `catch (Exception)` nor
   `catch (Throwable)` intercepts inside bsh. Those can only be caught by loading the script
   in the test harness, which is why the procedure extends the test rather than relying on
   runtime guards.

## Risks

- **Ordinary text is untouched**, by the same rule and with the same limits as the paste
  direction described in `WORD_GLYPHS.md`.
- **Every mouse selection now runs `phi_word_expand` over the selected text**, on the AWT
  thread. This is the reason `WORD_BOUNDARY_PLAN.md` must land first: at the committed
  implementation's speed — **measured** at about 3.5 microseconds per character — a 400,000
  character selection would freeze the editor for over a second, and 5 million characters for
  twenty seconds. After that plan's compiled-regex rewrite the same work takes single-digit
  milliseconds and about 100 ms respectively; its performance table carries the figures and
  says which corpus they were taken on, so read them there rather than copying them here.
  Note also that the trigger is wider than dragging: `dragged` is set by
  shift-click extension as well (`TextAreaMouseHandler.java:214`).
- **Adjacent glyphs**: `WORD_BOUNDARY_PLAN.md` repairs the 51 directly-adjacent sequences and
  leaves 9 `_`-bridged and 26 user-letter ones, which this plan inherits unchanged.
- **Platforms without a primary selection** get an unwrapped `DefaultRegister` at `%` after
  the first mouse selection; the install returns early and nothing is broken, but nothing is
  fixed there either.
- **The wrapper is installed once, at startup**, and nothing in jEdit replaces
  `registers['%']` afterwards — the static initialiser has already run, and
  `setRegister(char,Register)` (`:445-457`) simply stores into the array. Running the install
  twice is the hazard, handled by the per-wrapper `phi_sel` above.


## What is NOT verified

The real mouse gesture. Everything above was driven by calling `Registers.setRegister` and
`Registers.getRegister` directly; nobody has selected text with a mouse in a running
Isabelle/jEdit and middle-clicked it into a terminal. Two checks, on a Linux session with a
normal X11 desktop:

1. **Select a word glyph with the mouse** — drag across it; a plain click does not write the
   primary selection, see the `if(dragged && sel != null)` guard — and middle-click into a
   terminal or text editor. Expect the word in mathematical letters, not a blank box.
2. **Type mathematical letters by hand in another application** — do **not** reuse the text
   check 1 just published, because that string is character-for-character what the wrapper
   remembers and the memo would answer without `phi_word_fold` running at all — select them
   with the mouse, and middle-click into a `.thy` buffer. Expect the glyph. No preference has
   to be changed: Isabelle's site properties already set `view.middleMousePaste=true`.

Worth one extra look, because it is the default-on path this work changes: **middle-drag
quick copy** (`TextAreaMouseHandler.java:542-548`) — select a glyph, middle-drag it elsewhere
in the buffer, and confirm the glyph arrives as a glyph.


## Procedure

1. **Extend `phi_word_clipboard.bsh`** with `phi_install_primary_selection`, called from
   `phi_word_install` after the `n == 0` guard. About 35 lines, no new text-transformation
   logic. Every new bare name carries the `phi_` prefix, method locals included, and must not
   collide with a name another part of the script already owns.
2. **Extend `test_word_clipboard.bsh`** to cover, against a plain
   `java.awt.datatransfer.Clipboard` standing in for the selection:
   - a glyph written to the register comes out as letters and reads back as the glyph;
   - the glyph-against-unclaimed-letters case reads back exactly, via the memo;
   - a foreign string folds; ordinary text is untouched in both directions;
   - a foreign string that happens to equal the remembered expansion returns the remembered
     original — pin the behaviour rather than pretending it cannot happen;
   - `getTransferable` calls `getContents` exactly once, including on the failure path;
   - `setTransferable` does not propagate an exception from a clipboard that throws;
   - the install is a no-op when `Registers.getRegister('%')` is null;
   - running the install twice leaves the read-back correct;
   - the whole script still loads, and the existing round trip still passes.
   The suite runs under `xvfb-run` — `WORD_BOUNDARY_PLAN.md` makes that explicit in
   `run_word_clipboard_test.sh`, because touching `org.gjt.sp.jedit.Registers` at all runs a
   static initialiser that calls `getSystemClipboard()` and throws without a display.
3. **Ask the user to run the two manual checks and the quick-copy look.**
4. **Update `../fonts/WORD_GLYPHS.md`** by striking one line. `WORD_BOUNDARY_PLAN.md`
   rewrites that paragraph into a list in which drag and drop, the primary selection and
   input-field paste are marked "covered by a plan not yet landed"; this plan strikes the
   primary-selection line. Do **not** write the step as "remove the primary selection from
   the list" — before plan 1 lands there is no such entry, and the earlier wording was
   unexecutable. Check at the same time whether the sentence about `Isabelle_RPC_Host.unicode`
   repairing a raw private-use character still names a live producer.
